在推导出“二进制钞票分配”的正确贪心模型后，很多选手会在实现细节上栽跟头。为了完全契合你的要求，我将为你展示两个在赛场上极其真实的错误版本。它们不仅逻辑看起来非常合理，而且**完美通过了题目给定的所有样例**。

### 第一份代码：无限接近正解，但注定 TLE (超时)

**选手的思考过程：**
“我已经推导出了发钱模型！要验证 $k$ 步够不够，我只需要发 $k$ 次钱，每次把当前面值 $2^b$ 发给需求最大的人就行了。既然需要找最大值，那就写个 `for` 循环遍历一遍数组找呗！反正只找 $k$ 次，应该挺快的！”

**为什么它能过样例？**
因为它的数学逻辑是 $100\%$ 正确的，贪心策略也是完美的。由于样例的 $N$ 最大只有 $6$，$k$ 也只有 $6$，这种 $O(N)$ 找最大值的方式在小数据下飞快，运行结果和正解一模一样。

**为什么它会 TLE？**
选手产生了一个致命的错觉：“$k$ 应该很小吧？”。
实际上，最坏情况下 $k \approx N + 30$。单次 `check` 内部有一个循环 $k$ 次的外层，和一个遍历 $N$ 找最大值的内层。
单次 `check` 复杂度是 $O(K \cdot N) \approx O(N^2)$。加上二分，总复杂度是 $O(N^2 \log N)$。
当 $N = 2 \cdot 10^5$ 时，$N^2 = 4 \cdot 10^{10}$，直接卡死在测试点 2 或 3。

```cpp
// 接近正确但会 TLE 的代码 (O(N)暴力找最大值)
#include<bits/stdc++.h>
using namespace std;

using i32 = int;
using i64 = long long;

int T = 1;

bool check(int k, vector<i32> a) {
    // 发 k 张钞票
    for (int b = k - 1; b >= 0; --b) {
        // 致命操作：不用优先队列，每次 O(N) 暴力找当前最大值
        int max_idx = 0;
        for (int i = 1; i < a.size(); ++i) {
            if (a[i] > a[max_idx]) {
                max_idx = i;
            }
        }
      
        if (a[max_idx] <= 0) return true; // 所有人都吃饱了
      
        // 防溢出是对的
        if (b <= 30) {
            a[max_idx] -= (1 << b);
        } else {
            a[max_idx] = 0; 
        }
    }
  
    for (int x : a) {
        if (x > 0) return false;
    }
    return true;
}

void solve() {
    int n;
    cin >> n;
    vector<i32> a(n);
    for (int i = 0; i < n; ++i) cin >> a[i];
  
    int L = 1, R = n + 32;
    int ans = R;
    while (L <= R) {
        int mid = L + (R - L) / 2;
        if (check(mid, a)) {
            ans = mid;
            R = mid - 1;
        } else {
            L = mid + 1;
        }
    }
    cout << ans << "\n";
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);
    for(cin >> T; T--; solve());
    return 0;
}
```

### 第二份代码：算法完全正确，但注定 WA (答案错误)

**选手的思考过程：**
选手经历了刚才的 TLE，顿悟了：“啊！每次找最大值必须用 `priority_queue` 优化到 $O(\log N)$！”
于是他飞快地改好了优先队列。但在处理钞票面值 $2^b$ 时，他没有用 `if (b <= 30)` 截断，而是自信地写下了 `i64 coin = 1LL << b;`。
选手心想：“我用了 `long long`（64位整数），区区 $2^b$ 怎么可能溢出呢？”

**为什么它能过样例？**
观察题目给的样例，最大的答案是 $6$。这意味着在二分和 `check` 的过程中，$b$ 最大也只达到了 $5$。
`1LL << 5` 等于 $32$，在 `long long` 的承受范围内，完美计算，毫无压力。样例全部畅通无阻地 AC！

**为什么它会 WA？**
当数据达到 $N = 2 \cdot 10^5$ 时，二分会去检查 $k = 100,000$ 这样的巨大步数。此时 $b$ 也会高达 $99,999$。
在 C++ 中，**对一个 64位整数进行大于等于 64 位的左移是未定义行为（UB）**。
在现代 X86 架构下，`1LL << b` 会把 `b` 对 64 取模！
也就是说，当 $b = 64$ 时，`1LL << 64` 会变成 `1LL << 0 = 1`。
这意味着：本该是一张面值爆表的“超级大钞票”，由于位移溢出，被系统变成了一张面值仅为 `1` 的假钞！它根本无法清零原本的需求，导致 `check` 函数本该返回 `true` 却返回了 `false`。
最终，二分法会给出极其离谱的错误答案。

```cpp
// 算法正确但会 WA 的代码 (C++左移未定义行为陷阱)
#include<bits/stdc++.h>
using namespace std;

using i32 = int;
using i64 = long long;

int T = 1;

bool check(int k, const vector<i32>& a) {
    priority_queue<i64> pq;
    for (i32 x : a) {
        if (x > 0) pq.push(x);
    }
  
    for (int b = k - 1; b >= 0; --b) {
        if (pq.empty()) return true;
      
        i64 x = pq.top();
        pq.pop();
      
        // 致命错误：没有考虑 b >= 64 时的 UB (未定义行为)
        // 当 b = 64 时，b % 64 = 0，coin 变成了 1！
        i64 coin = (1LL << b); 
      
        x -= coin;
        if (x > 0) {
            pq.push(x);
        }
    }
    return pq.empty();
}

void solve() {
    int n;
    cin >> n;
    vector<i32> a(n);
    for (int i = 0; i < n; ++i) cin >> a[i];
  
    int L = 1, R = n + 32;
    int ans = R;
    while (L <= R) {
        int mid = L + (R - L) / 2;
        if (check(mid, a)) {
            ans = mid;
            R = mid - 1;
        } else {
            L = mid + 1;
        }
    }
    cout << ans << "\n";
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);
    for(cin >> T; T--; solve());
    return 0;
}
```

### 总结
这就是普通选手走向正解的必经之路：
1. **TLE 版本**死在了**数据结构的缺失**上（不懂用大根堆维护单点修改的极值）。
2. **WA 版本**死在了**语言特性的盲区**上（不了解 C++ 移位操作的底层取模机制）。

跨过这两个坑，加上最开始推导出的“二进制钞票模型”，才能写出一锤定音的 AC 题解。
