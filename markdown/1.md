补充知识：两个独立性详解
物理独立性：指用户的应用程序与存储在磁盘上的数据库中的数据相互独立。当数据的物理存储结构改变时（如更换存储设备、改变存取方式），应用程序无需改变，DBMS负责在模式/内模式映像中完成转换。
逻辑独立性：指用户的应用程序与数据库的逻辑结构相互独立。当数据的总体逻辑结构改变时，用户的局部逻辑结构可以保持不变，应用程序无需修改，DBMS负责在外模式/模式映像中完成转换。

一、函数依赖相关概念


概念

定义

函数依赖

属性X的值决定属性Y的值，记作 X→Y

完全函数依赖

如果X→Y，且X的任何真子集都不能决定Y，则称Y完全依赖于X

部分函数依赖

如果X→Y，且X的某个真子集也能决定Y，则称Y部分依赖于X

传递函数依赖

如果X→Y，Y→Z，且Y不包含于X，则称Z传递依赖于X



二、范式（NF）判断标准


范式

核心要求

1NF

每个属性都是不可分的基本数据项（最基本要求，所有关系模式都满足）

2NF

在1NF基础上，消除非主属性对主码的部分函数依赖

3NF

在2NF基础上，消除非主属性对主码的传递函数依赖

BCNF

在3NF基础上，消除主属性对候选码的部分函数依赖和传递函数依赖（即所有属性都完全依赖于候选码）



三、范式判断步骤


原始表（可能0NF）

↓ 消除重复组（1NF）1NF

↓ 消除部分依赖（2NF）2NF

↓ 消除传递依赖（3NF）3NF

↓ 消除所有非候选码决定因素（BCNF）BCNF



补充：如果要求在3NF或BCNF但当前达不到，需要进行模式分解，将表拆分成多个模式。

第11章 并发控制（重要！搭配第10章理解）




一、并发控制概述
事务是并发控制的基本单位。并发控制机制通过对事务并发操作的正确调度，保证事务的隔离性和数据库的一致性。

经典问题——飞机售票例子：

甲售票点 (T1) 和乙售票点 (T2) 同时读取机票余额 A=16。T1 卖出一张后写入 A=15，T2 也卖出一张后同样写入 A=15。实际卖出两张票，但数据库余额只减少了 1。原因在于 T1 的修改被 T2 覆盖了，这就是并发操作带来的不一致性。



二、并发操作带来的三种不一致性
符号约定：R(X) 表示读数据 X，W(X) 表示写数据 X。

问题通俗理解核心原因丢失修改你改完，我改，把你的覆盖了两个事务改同一数据，后写的覆盖先写的读脏数据读了别人还没提交（可能回滚）的数据读了临时数据，别人一撤消，你的数据就错了不可重复读同一查询两次结果不一样两次读之间，别人修改并提交了数据

1️⃣ 丢失修改

T1: 读(100)

T2: 读(100)

T2: 写(120) ✓

T1: 写(150) ✓ ← 覆盖了120

结果：T2的修改丢失



2️⃣ 读脏数据

T2: 读(100)

T2: 写(70) [未提交]

T1: 读(70) ← 读了临时数据

T2: 回滚(100)

结果：T1读到的是脏数据



3️⃣ 不可重复读

T1: 读(100)

T2: 读(100)

T2: 写(70) [提交]

T1: 读(70) ← 两次结果不同

结果：T1两次读不一样



三、封锁
封锁是实现并发控制的核心技术。事务在对数据对象操作前，先向系统请求加锁，加锁后其他事务在锁释放前无法更新（甚至无法读取）该数据。

两种基本锁类型
锁类型名称规则X 锁写锁（排他锁）只允许事务 T 读取和修改 A；其他事务不能加任何类型的锁，直到 T 释放 AS 锁读锁（共享锁）事务 T 可读 A 但不能修改 A；其他事务只能再加 S 锁，不能加 X 锁

相容矩阵
XS—XNNYSNYY—YYY

只有 S 与 S 之间是相容的（Y），其他涉及 X 的组合均不相容（N）。


四、三级封锁协议
封锁协议是对加锁规则（何时申请、封锁多久、何时释放）的约定。级别越高，一致性保障越强。

封锁协议规则可防止的问题一级修改数据 R 前必须加 X 锁，直到事务结束才释放；仅读数据不加锁丢失修改二级在一级基础上：读数据 R 前必须加 S 锁，读完即可释放丢失修改 + 脏读三级在一级基础上：读数据 R 前必须加 S 锁，直到事务结束才释放丢失修改 + 脏读 + 不可重复读

关键记忆点：

一级：只对写加 X 锁 → 防丢失修改
二级：对读加 S 锁，但读完立刻释放 → 防丢失修改 + 脏读（不能防不可重复读）
三级：对读加 S 锁，事务结束才释放 → 三者全防


五、活锁与死锁
1. 活锁
事务 T1 封锁数据 R，T2 请求封锁 R 进入等待；T3 也请求封锁 R；T1 释放后系统先批准 T3，T3 释放后又批准 T4，T2 可能永远等待——这就是活锁。

解决方法： 采用先来先服务策略，按请求封锁的先后次序排队，锁释放后优先批准队列中第一个事务。



2. 死锁
T1 封锁 R1，T2 封锁 R2；接着 T1 请求封锁 R2（因 T2 已封锁，等待），T2 请求封锁 R1（因 T1 已封锁，等待）。T1 等 T2，T2 等 T1，形成循环等待，两个事务永远无法结束。

死锁的预防：

方法做法缺点一次封锁法事务一次性将所有要用的数据全部加锁降低系统并发度，扩大封锁范围；且事务执行前难以预知需要哪些数据顺序封锁法预先规定数据对象的封锁顺序，按顺序加锁数据库中数据对象极多且动态变化，维护顺序成本高、难以实现

死锁的诊断与解除：

方法做法缺点超时法等待时间超过预设上限即认为发生死锁时间阈值难设定：太短误判死锁，太长意义不大等待图法用有向图动态反映事务等待情况，若图中出现回路则发生死锁—

解除死锁： 选择代价最小的事务将其撤销，释放其所有锁，使其他事务能继续运行。

等待图画法： 节点表示事务，有向边从等待者指向被等待者（如 T1 等待 T2，则画 T1 → T2）。图中出现回路即死锁。


六、并发调度的可串行性
可串行化调度： 多个事务的并发执行结果，与按某一顺序串行执行这些事务的结果相同，则该调度是正确的。
冲突操作： 不同事务对同一数据的读写操作（如 R(X) 与 W(X)）和写写操作（W(X) 与 W(X)）属于冲突。
冲突可串行化： 在保证冲突操作次序不变的前提下，通过交换不冲突操作的次序能得到一个串行调度，则为冲突可串行化调度。
重要结论： 冲突可串行化 → 一定是可串行化调度。但冲突可串行化是充分条件而非必要条件——存在可串行化但不满足冲突可串行化条件的调度。


七、两段锁协议
两段锁协议是数据库中普遍采用的并发控制方法，能保证并发调度的可串行化。

两个阶段：

扩展阶段： 事务可以申请获得任何数据项上的任何类型锁，但不能释放任何锁。
收缩阶段： 事务可以释放任何数据项上的任何锁，但不能再申请任何新锁。
核心原则： 在一个事务中，所有加锁操作必须全部发生在所有解锁操作之前。先全部申请→再全部释放，中间不能交叉。

判断标准： 若事务的封锁序列是连续申请锁再连续释放锁，则遵守两段锁协议；若加锁和释放交替出现，则不遵守。
